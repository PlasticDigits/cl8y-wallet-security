# Portal API v1

All requests use same-origin `/api/v1`. JSON timestamps are UTC RFC3339; amounts are decimal base-unit strings. Cookie `__Host-cw_session` is Secure, HttpOnly, SameSite=Strict, Path=/; mutation requests require exact configured Origin and `X-CSRF-Token` from GET `/me`. No wallet keys ever reach the service. Profile roles never grant token authority. Server never signs or submits privileged token actions.

POST `/auth/challenge` `{address, purpose:"login"|"add_wallet"|"assignment:<uuid>"}` returns `{id, message, expires_at, chain_id}`. For authenticated purposes, include CSRF. Sign `message` with ADR-036 `signArbitrary(chain_id,address,message)`. POST `/auth/verify` `{id, public_key, signature}` (base64 compressed secp256k1 and compact 64-byte signature) verifies the exact canonical ADR-036 SignDoc; login returns `{csrf_token}`, other proofs `{verified:true}`. Challenge binds configured HTTPS origin, chain, purpose, profile, address, nonce, audience and expiry. Used/expired challenges fail. Login wallet is immutable profile anchor; every added wallet independently proves control.

GET `/me` returns `{authenticated,csrf_token?,profile_id?,anchor_wallet?,wallets:Wallet[],assignments:Assignment[],contacts:ContactStatus[],chain:ChainStatus}`. Wallet `{address,verified_at}`. Assignment `{id,owner_wallet,candidate_wallet,role,status,proposed_at,executable_at,accepted_at?,delay_seconds}`. Role `guardian|recovery|notification`. Status `awaiting_consent|pending|active|cancelled|removed`. POST `/assignments` `{candidate_wallet,role}` starts a 24h minimum profile assignment delay with anchor as owner. Candidate signs challenge purpose `assignment:<id>`; possession consent cannot change target/role/deadline. GET `/me` reflects effective active status only after consent AND deadline. POST `/assignments/:id/cancel` cancels a proposal or starts delayed removal of active assignment, preserving protection meanwhile. Replacement is a new immutable proposal and a fresh full delay. No off-chain assignment can unlock tokens.

GET `/status` returns `{source_sha,chain,notifications,worker}`; chain `{status:"unavailable"|"ready",chain_id,reason,contracts:[]}`. Until allowlisted verified deployment configuration and ABI integration exist, chain status stays unavailable and no transaction preview can claim live defaults. Proposed defaults are not effective settings.

POST `/contacts/email` `{address}` requests double opt-in. POST `/contacts/email/verify` `{token}` confirms possession. POST `/contacts/telegram` starts one-use bot pairing. POST `/contacts/:id/remove` starts delayed removal, warning old verified contacts immediately. Delivery-disabled responses must explicitly report readiness; never pretend a verification was sent. Contact addresses/chat IDs and verification secrets are never returned by GET `/me`. Contacts cannot confer wallet/recovery authority. Detailed provider implementation follows foundation.

Authentication errors are generic `{error}` without identity/contact details. Sensitive writes have per-session/address bounded database rate limits. Server-side session expiry is absolute, logout POST `/auth/logout` revokes it. No cross-origin API access. Chain read settings/endpoints are operator-controlled only, never request URLs.
