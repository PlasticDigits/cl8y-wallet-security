# Security and privacy operating contract

Wallet proof uses ADR-036 canonical SignDoc, compressed secp256k1-derived Terra address, exact HTTPS origin/chain/audience/purpose/profile/nonce/expiry, five-minute one-use database challenge, and eight-hour opaque Secure HttpOnly SameSite Strict sessions. Mutations require exact origin plus session CSRF. Proxy forwarding is accepted only from the exact configured proxy DNS identity; all other forwarding headers are ignored. Traefik must overwrite X-Real-IP. Refresh/redeploy the API after proxy IP changes. Actual proxy sanitization is a deployment evidence gate. Admission bounds per-client and global storage growth without giving attackers a victim-address quota.

The first proven wallet is the immutable profile anchor. Added proven wallets do not gain anchor-session authority, and an existing separate wallet profile is never silently merged. A wallet already associated with another profile cannot be reassigned through this API. Losing the anchor currently loses profile write access; there is no contact/KYC/social override or server-issued recovery. Blockchain protection/authority remains independent and can be managed directly by the relevant on-chain wallet/governance. A future secure profile migration/recovery protocol requires separate independent proofs and review; do not fabricate it through support or contact access.

Profile guardian/recovery/notification assignments are notification/profile metadata only. Each candidate signs the immutable assignment nonce; a 24h minimum old-delay snapshot and candidate consent both apply. Active removal retains the old assignment until its old delay expires. Replacement restarts a new full delay. No profile timer unlocks tokens.

Contacts are AES-256-GCM encrypted with random nonces and a workload-only 32-byte key. Verification secrets are hashed in lookup tables and temporarily encrypted in delivery payloads, then erased after delivery/expiry. HMAC destination cooldowns prevent cross-profile verification floods without a public plaintext email index; a durable global verification budget applies before queue insertion. Do not log request bodies, addresses, chat IDs, provider URLs/errors, verification codes, raw evidence, or environment values. The portal stores no KYC documents or recovery evidence; private adjudication is a separate future feature.

Email uses Resend double opt-in; Telegram uses a one-use /start pairing followed by code confirmation in the authenticated portal. Previous verified channels receive contact-change timer warnings; newly confirmed replacement/additional channels wait the existing delay and never silently disable old channels. Warnings are transactional, high priority, and one per distinct dangerous timer; no transfer spam/digest hides security starts. Pending/failed/overflow counts remain visible. Configuring providers permits future explicit product-user opt-in notices. Operator tests must use only owned/sandbox recipients; no real-recipient test sends are authorized.

Outbox workers claim one item at a time with a unique lease fence. Resend retries use a stable idempotency key, eight bounded attempts and capped backoff within the provider's deduplication window. Telegram has no provider idempotency primitive: ambiguous network outcomes or expired in-flight leases become visible delivery uncertainty and are never silently replayed. Exactly-once external delivery cannot be claimed across a provider crash window. Provider rejection/uncertainty requires agent investigation; preserve the event identity and outcome. No provider response containing PII is logged.

Active verified contacts remain until explicit delayed removal. Removed/unverified/deleted contact ciphertext is erased after 30 days; undelivered notices then become explicit retention-expired failures. Auth challenges retain at most seven days; expired sessions one day; consumed/expired verification lookup rows one day; HMAC cooldowns one day after expiry. Backup retention is seven daily snapshots, so erasure completes after the last snapshot expires. Backups contain encrypted contacts and authentication hashes; keep DB credentials and contact key separately under authorized workload custody. Rotate the contact key only with an agent-owned re-encryption/backup compatibility procedure. Never publish PII, credentials or private incident material.
